# NBD prototype

Several installations of several accounts running NBD against an emulated PDS and Spaces host, in one deterministic in-memory simulation ([TODO-18](../TODOs.md#todo-18)). Unlike the [Python model](../model/README.md), each installation sees only what it verifies from repos when it syncs, so partial views and delayed observations are real. It is informative: where it and the specification disagree, one of them is wrong.

## For reviewers

### Running it

You need Node.js 20 or later. From this directory:

```bash
npm install
```

```bash
npm run dev
```

Open <http://localhost:5199>, pick a scenario from the menu, and press **Start**, then **Next step**. Each step narrates what to notice and shows its checks passing or failing, along with any invariant or goal violations. When a scenario ends, every control keeps working, so you can continue by hand. The URL records the scenario and step: `http://localhost:5199/?scenario=old-key&step=5` opens scenario 5 at step 5, so links can be shared between reviewers running it locally.

The **Trust** tab is the most useful view: rows are installations, columns are every device ever published, and each cell is that installation's own decision (● own, ✓ accepted, ⏳ held, ✕ revoked, ? unlinked). Disagreements between installations, such as one holding while another accepts, are visible at a glance. **Keys** shows who holds each space key and who granted it, **Repos** shows what each repo actually contains, and **Log** shows events, grant decisions, and violations. The **Sandbox** panel adds accounts and devices; the **Adversary and network** panel adds lag, malicious-PDS behavior, copied keys, takeovers, and backups.

To run every check instead:

```bash
npm test
```

### The UX app

A second app, Lantern, shows the [Relaxed](../ux-flows/relaxed.md) and [Paranoid](../ux-flows/paranoid.md) flows as a user would see them, drawn from the same simulation. With `npm run dev` running, open <http://localhost:5199/ux.html> for the device wall: one framed device per installation, each with its own inbox, spaces, device lists, notices, and alarms. Tap through them to post, join, invite, link and remove devices; the controls under each device and in the top bar take devices offline, add people and unlinked devices, and advance time, and the bar switches between Relaxed and Paranoid copy. In development, `window.nbdWorld` is the wall's live world.

<http://localhost:5199/ux.html?figures> lists the storyboard figures used in the flow documents, and `?figure=<id>` opens one. Each figure is a script of world actions with panels that show one device at one point in it, so a panel can only show a hold, notice, or lock state the protocol actually produced; `npm test` checks every panel's expectations. To regenerate the images in `ux-flows/images/` after changing a figure or the protocol (the first time, run `npx playwright install chromium`):

```bash
npm run capture
```

Pass figure ids, such as `npm run capture paranoid-adding-a-device`, to capture only those.

### What the checks enforce

The goal-level check (`src/sim/disclosure.ts`) judges every grant from an honest installation against the world's ground truth: who really controls each device, when it appeared, and which keys were copied. It ignores the clients' own reasoning. A grant to an attacker-controlled device must follow first contact, an elapsed 72-hour hold, an approval by a compromised device while the account still had a device the attacker does not control (the documented revoked-signer gap), or an approval by a live attacker device the issuer already accepted. Under the default policy, the first-contact excuse applies only to a record of the issuer's own account authorizing that device, or an approval ancestor of it, in that space ([grant standing](#grant-standing-and-invites)). No grant may go to a device the issuer's own view shows removed. The invariant monitor (`src/sim/invariants.ts`) checks each installation's trust decisions against its own observations: the single-root rule, approval closure, re-enrollment holds, justified acceptance and revocation, views that never roll back, and hold credit that never exceeds real time.

Under the [witness policy](#relay-witnessed-repos-proposal) a third check, `src/sim/detection.ts`, judges the proposal's goal: every impostor an honest installation accepted is alarmed on, or warned of, by each of its account's installations within 24 hours. All three run around every scenario step and every random-walk step. `test/disclosure.test.ts` shows the goal check flagging forbidden disclosures, and `node test/mutate.mjs --all` breaks trust rules one at a time to show the tests catch each.

### Grant standing and invites

The specification's [grant standing](../device-enrollment.md#grant-standing) and [invites](../core.md#invites), adopted from the inviters proposal, are the world's default policy, `"inviters"`. `new World(seed, { policy: "baseline" })`, or `policy: "baseline"` on a scenario, selects the rule from before them, which any first contact could grant under; it is kept for comparison. The rule's history and the review cases it closes are in the [rationale](../rationale.md#inviters-and-grant-standing). The baseline `traces/` and their walks, the baseline random walks, and the tests that contrast the two rules pin it explicitly. Scenarios 1–12 run under the default; two changed expectations because of it: in 6 (substitution) Carol, who didn't invite Bob, holds the substitute for 72 hours before disclosing it, and in 11 (eager pinning) the lazy member's late first contact is held instead of disclosing the space. The rule follows `InviterClient` in [`model/nbd_trust.py`](../model/nbd_trust.py), including the two refinements the model found ([findings](../model/README.md#what-the-inviters-variant-found)), the revision after Astra's second review (invites that must admit, pending invites, and durable invites), and the one after the third: each record authorizes exactly what was vouched when it was made.

- **Grant standing** (`Trust.standing(b, space)` in `trust.ts`) is checked by `authorizeExchange` only for the issuer role: without it, the result is `INCOMPLETE` with "first-contact hold". A binding has standing in a space when it is the installation's own account's, re-enrolled, held (72 hours credited to its own first-contact hold), authorized in that space by a published invite or capture record of its own account, or approved by a binding with standing there. Every binding accepted by first use, approval, or an invite record starts its own hold; a revoked binding's hold stops crediting and keeps its credit. Under this policy an installation credits time at the start of every sync, before any observation can revoke.
- **Authorization** (`TrustState.authorized`, space -> bindings) comes only from the installation's own account's published records: a record's `authorizes` list counts in that record's space, and nowhere else. A new invite authorizes the listed live bindings in the inviter's **first-contact lineage** (`TrustState.lineage` holds its roots; `Trust.inLineage`): bindings it accepted by first use at any time, adopted from an own record or an import for an account it had never pinned, or accepted by approval, directly or through a chain, from one of those, revoked or not, so a replacement phone stays in it. Re-enrolled bindings, a reset's held candidate, and own bindings never are. A capture authorizes exactly the captured bindings, and a pending invite nothing. Records are fixed when made: a later pin never extends an earlier record, whether that record authorized nothing, named other devices, or was a pending invite that expired. `TrustState.admitted` (spaces each account was admitted to by own records) is kept for display only.
- **Invites** (`Installation.invite`) are refused for an account that is already a member: an invite counts only if it admits. Otherwise the installation observes the account, pins it on first use if it has no pin for it, decides what the invite authorizes, and signs the record, once (`prepareInvite`). Its pins (lineage roots) are saved then, so a second invite prepared before the first is published still authorizes them. The entry goes into `inviteOutbox`, strictly first in, first out: a new record goes out at once only if the outbox is empty, and otherwise waits behind older entries; each sync resends the oldest byte for byte, stopping at the first failure; a lost acknowledgement is resolved by reading the repo back. Only once a record is published does the installation take its authorization and admit the account at the host. An entry whose account became a member meanwhile is abandoned unsent; abandoning a pending invite also ends its pending state and drops any capture queued for it. Inviting the same account to the same space again while its invite is unsent resumes that invite rather than preparing a second record.
- **Pending invites**: an invite of an account the installation never pinned and that has no device records is published with `pending: true` and no bindings, and remembered in `TrustState.pending` with time credited like a hold. The first time that installation pins the account, if the pending invite was made by this very device and has credited less than `PENDING_INVITE_TTL` (168 hours), it saves a capture record (`captures`: the pending record's rkey) authorizing them in the pending invite's space. The capture is saved to the outbox and published only once its pending invite has been published by this account (it waits otherwise), and never if that invite was abandoned. Pending state never transfers, by pairing, backup, or restore, even back to the device that made it; abandonments (`TrustState.abandoned`) do, so a stale backup cannot reopen one.
- **Other own installations** read invite records in every space where their account's PDS holds a repo for it, and trust a record only if it is signed by an own device they accepted (even if since removed). An installation that never pinned the account pins a record's `authorizes` as invited, as roots of its lineage, authorized in the record's space, and then keeps that account's pin current like a member's. One that already pins the account takes a record's authorization only for bindings in its own lineage. Imports follow the same rules, merging acceptance and approvers before judging imported authorizations, carry lineage roots only for accounts the importer never pinned, and carry first-contact holds as credited time.
- **The goal check** allows the first-contact excuse only when an invite or capture record of the issuer's account for that space authorizes the attacker device or an approval ancestor of it, and that device or one of its approval ancestors appeared before the issuing installation first knew the account: a first contact, not a reset. Otherwise the device must have appeared at least 72 hours earlier, or an existing approval excuse applies.
- **The invariant monitor** checks that every accepted binding has its own first-contact hold, credited no faster than real time since the device appeared, never falling, and frozen once revoked; that a lineage root is added only for an account the installation had never pinned, and never for its own account or a re-enrolled binding; that each admitted space comes from a published record that admitted the account; that a capture is published only by the device that made its pending invite; that every binding a published record authorizes, or an approval ancestor of it, appeared before the record's maker first knew the account; that every authorization an installation holds traces to a published own record for that space naming the binding, which is in its lineage; and that new standing is explained by such an authorization, an approval in the installation's verified view from a signer with standing there, or an elapsed hold.

#### Inviters traces

`traces-inviters/` holds shared-view inviters walks, regenerated and checked like `traces/` by `test/traces.test.ts`. Each fixture has the same shape as a baseline trace, plus:

- top level: `"policy": "inviters"` and `"spaces": ["A", "B"]` (A is Club, administered by Alice; B is Garden, administered by Carol). The viewer is Alice's first phone. Erin has no devices at the start.
- per step, `tracked`: the accounts (including Alice) whose repos the viewer follows: members of spaces it joined, accounts it invited, and accounts it adopted from an invite record. Only these have been through first use; replay should query `accepted`, `holds`, and standing only for them, since querying another account would pin it.
- per step, `standing`: for each space label, the bindings the viewer may grant that space's key to now.
- per step, `authorized`: for each space label, the bindings the viewer's own account's published records authorize there (`TrustState.authorized`), revoked or not.
- ops: the step's repo operations (deletions, approvals, additions) come first, then invite, flush, wait, and skew ops in the order they happened.
- an invite op: `{"op": "invite", "by": [account, deviceId], "space": "A" | "B", "account": name, "bindings": [[account, deviceId], ...], "authorizes": [[account, deviceId], ...], "pending": bool, "captures": bool, "published": bool}`. `captures` is true for a capture record. For the viewer, every attempt appears where it happened: an invite it made, or a capture it made on first meeting a pending invite's account, with `published` false if it did not go out at once: the first write failed, or older records were still unsent so it queued behind them. For any other device, a record appears once, when published, with `published` true. Step 0 holds the setup: four phones, then Alice inviting Bob to A and Carol inviting Dave to B.
- a flush op: `{"op": "flush"}` when the viewer published the oldest entry in its outbox, unchanged; `{"op": "flush", "abandoned": true}` when it dropped that entry unsent because its account had become a member of the space meanwhile (if that entry was a pending invite, its pending state ends and any capture queued for it is dropped too, with no op of its own). Resends that fail again record nothing. Inviting an account again while an invite of it to that space is still in the outbox resumes the outbox (a resend) and records no invite op of its own.

To replay one: add, approve, delete, wait, and skew as for baseline traces. For an invite op `by` the viewer with `captures` false, make the viewer's invite (its `authorizes` and `pending` should match), publishing it if `published` and otherwise saving it to the viewer's outbox; pins and lineage are saved at once, but the account is admitted and the authorization taken only on publication. A viewer op with `captures` true is a check: the viewer should itself have prepared that capture on first use of the account during this step, and published it if `published`. On a flush op, publish or abandon the oldest outbox entry. For any other device's op, append the record as given (inviter is `by`'s account). Every invite in these walks by one of Alice's devices comes from a device the viewer accepted, so the viewer may adopt any such record. A pending invite's window is credited from when the viewer made it, not when it was published.

### Relay-witnessed repos (proposal)

[proposal-reliable-detection.md](../proposal-reliable-detection.md) is modeled as a third world policy, `"witness"`: the inviters rule plus relay witnessing. `new World(seed, { policy: "witness" })`, or `policy: "witness"` on a scenario, selects it; the specified rule stays the default. Its goal: if any honest client accepts a device as yours that none of your installations generated, transferred, or approved, a running installation of yours alarms within 24 hours, or warns that it cannot check, and one that was not running does so when it next runs.

**World** (`src/world/relay.ts`):

- **The reference relay** is one ordered log. PDSes send public-repo commits to it as `#commit` events (operations with each path's previous value, the previous root, and `since`, the revision of the commit before it as the PDS states it) or `#sync` events (commit only). An honest PDS sends every commit, so its `since` is its true previous revision; `since` is not signed, so a malicious PDS can write anything there (a relay hook's `since`). Under this policy revisions are timestamps, as atproto's are: a commit's revision is its world time in microseconds (`revAt`), or one more than the previous revision if that is not lower. It verifies signatures on ingest, refuses revisions that go backward or lie more than `REV_ALLOWANCE` (5 minutes) ahead of its clock, stamps each event with its `time`, when it first sequenced the event, and keeps that time for every subscriber, however late delivered, and on every replay after a resume (the proposal's Reference relay requirement), skips sequence numbers now and then, delivers the same events to every subscriber, and keeps 72 hours for resumption (`RELAY_REPLAY_WINDOW`). An honest relay may deliver to a slow subscriber late (`relayDelay`): its events then arrive old. The simulated accounts are a sliver of the firehose, so the rest of the network's events are modeled as delivered continuously up to the same point, stamped the same way (`networkTime`): a healthy subscription is never idle. `World.relayTimeOnDelivery` makes it stamp each event with the time it sends it to the subscriber instead (`Relay.timeOnDelivery`), which the sync specification allows an honest relay and the proposal forbids the reference relay: a replay or a backlog then carries fresh times. It serves no repos. Like an honest relay under a rate limit, it can drop an account's next commits (`World.relayDrops`); `World.uncheckedRelay` makes it check neither of an account's revision rules, as the sync specification asks of relays but doesn't make them do.
- **A witness per application** (`Witness`: `lantern`, `other`, and `attacker`, which attacker-run installations use) tails it with a subscription cursor. It reconstructs each account's public repo at each commit's exact root: a `#commit` by applying its operations to the previous reconstructed state and checking the result against the commit's root (and by inversion); one whose previous root isn't that state's, as after a commit the relay dropped, is a gap; one whose `since` names a revision other than that state's records a gap before it (the relay may have dropped commits that changed nothing or cancelled out, leaving the root as it was), though the commit itself is reconstructed from its operations; a `#sync`, or a `#commit` with no usable previous state, by fetching the repo from the PDS and checking it against that exact root. A fetch that isn't answered leaves the commit **awaiting a fetch**: the account's later events wait behind it, and after `FETCH_TIMEOUT` (1 hour) it is a gap. Anything else is a **gap**, kept permanently, covering the revisions from just after the last one it recorded through the commit's own, so a commit the relay dropped before it lies inside it. A commit whose revision is more than `REV_ALLOWANCE` ahead of its event's relay `time` is not taken into the history: it opens a gap, closed at the next revision the witness records, without an alarm and without raising the account's latest revision, and the next commit is reconstructed as one after a gap. A commit whose revision is not above the account's latest is a gap at that revision and an **integrity alarm**, which the witness reports with every answer for the account, whatever cursor it is asked from (`HistoryResponse.integrity`). A resume the relay refuses (an outage beyond the replay window) is a **stream gap**, after which the witness resynchronizes each account at the relay's latest published commit. Every account gets a gap, from just after its last revision through `REV_ALLOWANCE` past the relay time at which the witness resumed, or through the revision it resynchronizes at if that is higher: the relay may have carried any revision up to there, whatever revision the account resumes at. A cursor moves past the gap only to the revision it resynchronized at (`resync`), so a commit relayed afterward with a revision inside the interval is still read, and the gap is served to any cursor its interval reaches. Resuming below the revision held is also an integrity alarm. A witness that started following the relay late (`World.lateWitness`), was rebuilt (`World.rebuildWitness`: it loses its state and starts following again), or met an account only after a stream gap, reports the history it lacks as a gap bounded the same way (`start`): from the account's first revision through `REV_ALLOWANCE` past the relay time at which it started following, or through its **starting revision** (the relay's latest published commit for the account then) if that is higher; a cursor moves past it only to the starting revision, and it is served to any cursor its interval reaches, including one at the starting revision. It carries the starting commit and the relay time at which the witness started following the account (`followedFrom`), and every entry the relay time of the commit at its position (`time`). Its **frontier** for an account is the relay `time` on the newest event it has processed in order, the rest of the network's included (`lag` hours behind what was delivered, if it lags), or, while a commit for the account awaits a fetch, that commit's time; with every answer it reports the **frontier age**, its own clock minus that frontier. A frontier more than `CLOCK_SKEW` (5 minutes) ahead of its clock is a fault it reports, and the frontier age is then infinite. History entries are served by position, the account's **repo revision**, and it retains them for `WITNESS_RETENTION` (90 days), saying up to which revision it pruned what a cursor asks for. `setWitness` gives it outages, unreachability from clients, lag, a clock offset, or a page size for history answers.
- **Malicious PDS behaviors** (`World`): `forkedImpostor` sends the relay (and a chosen client) a fork in which every device is replaced by the PDS's own, while serving everyone else, including the account's own devices, the real repo; `publishSyncRoot`/`replaceSyncRoot` publish a `#sync` root with an impostor, serve it only to chosen witnesses and serve every other witness its replacement, then publish the replacement; `syncReplaced` does both before any witness fetches; `serveAt` serves chosen clients the PDS's commit at a given revision; `commitAtRev` commits once at a revision the PDS chooses, outside its sequence, and `futureCommit` does so hours ahead, through an unchecked relay (a PDS clock briefly wrong); `replayRevision` rolls the repo back to an earlier commit and sends that commit to the relay again, which an unchecked relay publishes a second time; `withholdFetch` refuses one witness's fetches; `unrelayedImpostor` signs a commit it never sends the relay and serves it to a client; `flashImpostor` publishes an impostor in an ordinary commit and later deletes it, hidden from the account's own devices; `impostorAtRev` publishes one at a revision the PDS chooses, through an unchecked relay. A `RogueWitness` per PDS vouches for whatever that PDS serves, for the mutation that trusts it. Out of reach: `dishonestWitness` (a witness that omits an account's commits), and the relay's `hideFrom`.

**Installations** (`src/protocol/installation.ts`, state in `src/protocol/witness.ts`): each trusts exactly its application's witness (`Installation.app`). Under the policy it never observes a PDS-served snapshot. For every tracked account it reads the witness's history from a saved cursor, a repo revision, and processes every entry in order, applying each reconstructed state and recording each gap; an account met for the first time starts at its latest published commit, which must be reconstructed (otherwise `INCOMPLETE`). It still fetches the PDS's commit and compares it with the witness's commit at that revision (`commitAt`): a difference is a fork alarm; a commit strictly between two commits the witness reconstructed consecutively, the later from a `#commit` whose `since` named the earlier's revision and whose operations inverted to the earlier's root, with no gap between, is an `unrelayed-commit` alarm, the PDS's commit and the two revisions around it kept as proof (`unrelayedProofs`); one inside a recorded gap, including a commit the witness didn't accept for its revision, is neither an alarm nor `INCOMPLETE`; one above the witness's latest is `INCOMPLETE`. A witness's integrity alarms become `relay-integrity` alarms for every installation following the account. With each cursor it keeps the relay time of the commit that set it (`mon.cursorTimes`, carried by backups and pairing); a cursor set by a commit the relay sequenced before a witness started following the account, and above the revision the witness's history starts at, or at it with a different commit, is also a `relay-integrity` alarm, with the starting commit kept as proof (`startProofs`), and a gap from the starting revision through the cursor. A cursor set after the witness started needs no check. For its own account, every reconstructed commit goes through the baseline own-account alarms and notices, so a device present only briefly, or its own deletion, alarms. Own-account gaps are gap warnings, each acknowledgeable on its own (`gapWarnings`, `acknowledgeGap`); pinned accounts' gaps are audit intervals (`mon.auditGaps`). The monitoring frontier advances only after a complete answer, and only to better coverage; **coverage age** is the frontier age at the last advance plus monotonic time since the installation sent the request that produced that answer (for an answer in several pages, the first page's, with the one frontier age computed when that request arrived), so an answer delayed in transit (`World.witnessTransit`: computed when the request arrives, delivered hours later) can't make old coverage look fresh. A late answer whose frontier is older than the coverage held changes nothing, and an answer to a request sent before a restart is discarded (each request carries an id its answer echoes). Coverage is carried across a restart by the wall-clock interval since the last checkpoint, and unknown (treated as over any limit) if that interval is negative. `liveness()` is the non-dismissible warning whenever coverage age exceeds 24 hours, naming the cause: the witness is unreachable, behind the relay, waiting on a fetch, or reporting a clock fault. A fresh enrollment replays the retained history and presents every binding that appeared and was later deleted (`history-binding` notices; current ones alarm or go on the start-over list as before), with a gap warning for history the witness no longer holds or never had; pairing resumes the approver's cursors; backups carry the cursors, gaps, and coverage checkpoint, and a restore resumes from them. Cursors are revisions, the same at every witness, so a restore or pairing may use another application's witness (`restore(..., { app })`, `install(..., { link, app })`); whatever part of the history after the cursor that witness lacks, pruned or from before it started, is a gap warning for those revisions. Under this policy time passes in hourly settles, since installations SHOULD check at least hourly.

**The goal check** (`src/sim/detection.ts`, run by the invariant monitor after every scenario, walk, and fuzz step under the policy): for every device an honest installation accepted for account A that the attacker or a malicious PDS controls, accepted at time t on the witnessed commit at revision s of A's repo, each honest installation of A whose state began by t (a restored one inherits its backup's start and counts what its lost predecessor did; a device linked later is new, since its approver read that history) must, by t + 24h if it was running then, or by the start of its next run, have alarmed about the device or presented it, recorded a gap warning whose revisions cover s, or shown the liveness warning while its own history stopped before revision s. It also checks that the commit an acceptance relied on was reconstructed by the accepting installation's witness with the device in it. Obligations whose owner's witness or relay is dishonest are skipped: the goal assumes both honest. Under other policies only an alarm can meet it, which is how the comparison scenarios show the specified rule missing a case.

#### What the witness policy found

Proposal flaws:

1. **Live is measured against what the relay delivered, not the relay's head** (Witness progress). An honest relay with a backlog for one subscriber, a slow consumer whose pings still arrive, leaves that witness live with frontier age zero while it is behind every other witness. `witness.test.ts` "FINDING: an honest relay that delivers…": Bob's witness's events arrive 30 hours late; Carol's app accepts a forked impostor at hour 0; at hour 25 Bob's phone has neither alarmed nor warned, with coverage age under an hour, and the goal check flags it (it alarms at hour 30). Suggested text at the time: a witness is live only if it has processed every event up to a relay head it learned within the last 60 seconds. **Rule changed:** the proposal now measures the frontier by the relay's own `time` on the newest event the witness has processed, so the backlog shows up as old events arriving. The test (now "an honest relay that delivers to Bob's witness 30h late…") shows Bob's phone warning within 24 hours, and the goal check passing; slow relay delivery is now in the adversarial walks.
2. **Fresh enrollment after retention is silent** (Watching your own account). The proposal says a brand-new account that has bindings in its history was impersonated, but if the user's first device enrolls more than `WITNESS_RETENTION` after an impostor was published and deleted, the replay finds nothing and nothing warns. `witness.test.ts` "FINDING: a fresh enrollment after retention…". Suggested text: a fresh enrollment also raises a gap warning for any part of the account's history older than the witness retains. **Rule changed:** the proposal now treats any history the witness lacks as a gap, and the prototype warns (`witness.test.ts` "a fresh enrollment after retention warns…").

Ambiguities, and the reading taken:

3. **A `#commit` with no usable previous state, and recovery after a stream gap.** Read literally, a `#commit` is reconstructed only from the previous reconstructed state, so after any gap every later `#commit` is a gap too, forever, and a pinned account can never be met again (its latest commit is never reconstructed). The prototype also reconstructs such a `#commit` by fetching the repo at its exact root, and after a stream gap resynchronizes each account at the relay's latest published commit (`getLatestCommit`) with a verified fetch. Suggested text under Reconstructed commits: "a `#commit` whose previous state is unknown is reconstructed like a `#sync`; after a stream gap, the witness restarts each account from the relay's latest published commit for it."
4. **Inversion.** Applying a commit's operations to the previous state and reversing them always yields the previous root, so the check as worded binds nothing; what binds the operations to the commit is that the result matches the commit's root. A mutation that drops that comparison and keeps only inversion lets operations that omit a device record reconstruct a wrong state. Suggested text: "the result must match the commit's root (and, from the commit's blocks, the reversed operations must produce the previous root)".
5. **Where a pinned account's history starts.** The proposal says where the own account's history starts but not a newly met account's. The prototype starts at the latest published commit and requires it to be reconstructed; if it is a gap, first use is `INCOMPLETE` until the account publishes again, which lets a PDS make its account impossible to meet (a denial of service it already has).
6. **A restore "older than retention".** The prototype warns when the witness no longer holds history after the backup's cursor (it pruned the account's commits past it), not merely because the backup is old; with no commits to the account in the interval, nothing was lost and nothing warns. With cursors as revisions this is per account: commits to other accounts no longer count (scenario 35 now links two of Bob's devices after the backup).
7. **Pending fetches.** The proposal doesn't say whether a witness may report itself live while a `#sync` fetch is outstanding. The prototype fetches synchronously, so an unanswered fetch holds the witness's processing; a witness that fetched asynchronously and still counted as live could let the frontier pass a commit that is neither reconstructed nor a gap (question 4). Suggested text: a commit whose fetch is outstanding is unprocessed until it is reconstructed or, after a timeout, recorded as a gap. **Adopted:** fetches are now asynchronous; a commit awaiting one holds its account's frontier (only), and after `FETCH_TIMEOUT` is a gap.
8. **An account followed before it was pinned.** An installation can hold a cursor for an account it never pinned: one invited while it had no devices, or a cursor copied by pairing. Processing that history in order would first-use the first device ever published, and hold a quick takeover's device as a reset; starting at the latest commit first-uses the takeover's device. The proposal doesn't say. The prototype meets any account it never pinned at its latest published commit, matching the specified rule (and the model's replay); processing a pending invite's account from the invite's cursor would be stronger and is worth considering.

Findings on the event-time frontier and revision cursors:

9. **A stream gap in every account's history.** After a refused resume the witness resynchronizes each account at the relay's latest published commit. If that revision is the one it already held, nothing was published meanwhile (revisions only increase) and nothing was missed, so the prototype reported the stream gap only for accounts whose latest revision changed. Read literally ("a gap in every account's history"), every user of the application gets a gap warning after any long outage, which is exactly the habituation to harmless gaps the proposal warns about. Suggested text at the time: "a stream gap is a gap in the history of every account whose latest published commit changed across it". **Rule changed back:** the proposal adopted that exemption, and has now removed it: revisions increase only if the relay enforces it, and one that doesn't lets a PDS publish an impostor and then the original revision again while the witness is away (finding 20). The habituation cost stands: every user of the application gets a gap warning after an outage beyond the replay window (`witness.test.ts` "an honest relay's stream gap…").
10. **Gap intervals in revisions.** Revisions increase but are not consecutive (they are timestamps), so a witness that resynchronizes an account at revision R after a break can't say which revisions it missed, only that they lie after its last one and up to R. The prototype records such a gap through R (its consecutive integer revisions would otherwise make the interval look empty), and a history-start gap as everything before the first revision it holds (now bounded like a stream gap: finding 24). The proposal should say that gaps are reported as revision intervals and how their ends are inclusive.
11. **Where a late witness's history starts, in revisions.** A witness that starts late (or after a stream gap) and is asked about an account it has seen no event for since can only say where its history starts as a revision by asking the relay for the account's latest commit (`getLatestCommit`) and reconstructing it. The prototype does that lazily on the first request. Without it, a restore or pairing onto that witness, for an account quiet since the witness started, has no revision to compare its cursor with.
12. **"Frontier has passed its revision"** (Decisions on witnessed state). The frontier is a relay time; a PDS-served commit carries a revision, a timestamp on the PDS's clock, so the two can't be compared directly. The prototype doesn't implement this integrity alarm (an unreported commit stays `INCOMPLETE`). Suggested text: "when the witness has reported a later revision of the account but never the served one", which needs no clock. **Rule changed:** the alarm is now narrowed to a served commit strictly between two commits the witness reconstructed consecutively, with no gap recorded between them; a dropped commit falls inside a gap. The prototype implements it (see the table above, and findings 15–16 on where "consecutively" needs care).
13. **The pending-fetch rule and the deadline.** With `FETCH_TIMEOUT` (1 hour) well under the 24-hour limit, a witness that let the frontier pass a commit awaiting a fetch would still meet the goal: the commit becomes a gap warning an hour later. The mutation that does this is caught only by a direct check of the reported frontier, not by the goal check. Holding the frontier matters for naming the cause in the liveness warning, for finding 12, and if the timeout is ever raised toward 24 hours.
14. **The clock-skew fault's effect on installations.** A frontier age that "counts as exceeding any limit" doesn't advance an installation's frontier, so its coverage age keeps counting from its last good report and the warning shows up to 24 hours after the fault began, not at once. The prototype reads it that way, and names the clock fault in the warning. A witness clock running ahead only inflates frontier age (earlier warnings), which is not a fault. A witness clock running slow by more than its backlog would otherwise hide the backlog entirely (`witness.test.ts` "a slow witness clock can't hide a backlog…").

Findings on unrelayed commits and revision checks:

15. **A `#sync` after a dropped commit** (Decisions on witnessed state). An honest relay drops commit X; the PDS's next event is a `#sync`, which carries no operations, so nothing fails against the witness's state and no gap is recorded. Counting the commit reconstructed from the `#sync` as consecutive with the one before X made a PDS serving X, honestly, a false integrity alarm (`witness.test.ts` "a dropped commit followed by a #sync…", mutation "a #sync counts as consecutive"). **Rule changed:** the pair counts only when the later is a `#commit` whose operations inverted to the earlier. The cost: a PDS can follow an unrelayed commit with a `#sync` and avoid the alarm (the commit is still never accepted, since it was never reconstructed).
16. **A dropped commit that changes nothing.** The rule relies on the next commit's operations failing inversion, but a commit that changes no record (in the prototype, the commit a key rotation issues) leaves the root as it was, so the next commit's operations still invert to the witness's state and the dropped commit sits between consecutive reconstructions: serving it was a false alarm (`witness.test.ts` "a dropped commit that changes nothing…"). atproto's `#commit` carries `since`, the revision of the PDS's previous commit, which would show the drop as a gap. **Rule changed:** the proposal at first exempted a served commit whose data is the earlier commit's (a commit that changes nothing hides nothing), and has now replaced the exemption with `since` (finding 25).
17. **The integrity alarm for a non-increasing revision sits below the cursor.** A gap recorded at a revision not above the account's latest lies at or below the cursor of every installation already past it, so an installation reading history from its cursor never sees it, which is the case the rule exists for. The prototype reports a witness's integrity alarms for an account with every answer, whatever the cursor (mutation "integrity alarms only from history after the cursor"). The proposal should say how the alarm reaches installations.
18. **Restarting at a commit beyond the allowance.** After a stream gap, or when a late witness meets an account, it restarts from the relay's latest published commit, which may be one beyond `REV_ALLOWANCE`. Taken as the restart point, its revision would become the account's latest, which the allowance rule exists to prevent; the prototype restarts from the latest commit within the allowance. Suggested text: "...restarts each account from the relay's latest published commit for it within `REV_ALLOWANCE` of its event's `time`." Also, a relay that publishes a far-future revision but enforces increasing revisions (rather than neither check) refuses every later honest commit for the account; no witness rule helps there, and the account goes quiet (its PDS-served commits stay `INCOMPLETE`), a denial of service the PDS can't cause on an honest relay. Similarly, a client meeting an account afresh while its head is a commit not accepted for its revision finds no reconstructed latest commit and is `INCOMPLETE` until the account commits again (as with any gap at the head, finding 5); a client that already pins the account and is served that head is neither alarmed nor `INCOMPLETE`.
19. **A served commit below the account's first relayed commit**, at a witness that holds the account's history from its first event, is not between two reconstructed commits, so it raises no alarm, though the witness knows the relay published nothing there either. Harmless (no client accepts it), but the rule could cover it: "...or below the first commit of an account whose history the witness holds from its first event".

Findings from Astra's second review (same-revision stream gaps, reference-relay timestamps, time in transit):

20. **A same-revision stream gap is an empty interval, at the cursor.** With the exemption gone, the rule text still yielded no warning: "a gap is a revision interval: from just after the last revision the witness reconstructed for the account, through the first revision it reconstructed again" is empty when the two are the same revision R, and an installation already at R reads history after its cursor, where a gap at R never appears. `witness.test.ts` "an impostor published and the original revision replayed…": Bob's phone and witness are offline; his PDS publishes an impostor through a relay that doesn't check revisions, Carol's app accepts it, the PDS publishes revision R again, and 73 hours later the witness resumes at R. The PDS can also replay an earlier revision R0 < R; the witness then resumes below what it held, which the non-increasing-revision rule doesn't clearly cover, since resynchronizing isn't seeing a commit in the stream ("an earlier revision replayed…"; the prototype raises an integrity alarm, mutation "resync below the revision held raises no alarm"; suggested text: "a restart below the last revision reconstructed is also an integrity alarm").
21. **A stream gap's revisions didn't bound what it hides.** Even a non-empty interval ending at the revision resynchronized at misses an impostor above it: the model's minimal case is an original r0, an impostor r2 that Carol accepts, then any commit r0 < r < r2, all during the outage; the witness resumes at r ("an impostor Bob's PDS published, then any commit below it…"). **Rule changed:** a stream gap's interval now runs through `REV_ALLOWANCE` past the relay time at which the witness resumed, or the revision it resynchronizes at if higher, and an installation's cursor moves past it only to the revision resynchronized at. The prototype follows both (mutations "stream gap ends at the resync revision", "cursor moves to a stream gap's end": with the cursor at the gap's end, a commit relayed just after the resume, inside the interval, is never read). It also serves a stream gap to any cursor its interval reaches, which the same-revision case needs since the gap's position is the cursor itself (mutation "stream gap served only after the cursor"); the proposal says only that a stream gap is "reported". The cost: every account's gap now reaches past its next few minutes of honest commits, and an honest relay's outage still warns every user (finding 9).
22. **Which page's frontier age.** Coverage age counts from the first page's request, but each page reported a frontier age and the rule said only "the frontier age the witness reported". **Rule changed:** a paged answer carries one frontier age, computed when the first page's request arrives; a late answer whose frontier is older than the coverage held doesn't move coverage back; an answer to a request sent before a restart is discarded. The prototype implements each (mutations "paged answer takes the last page's frontier age", "a late answer moves coverage back", "an answer from before a restart accepted"); answers echo their request's id, which is how an installation recognizes a stale one. In the prototype a fresh enrollment whose answer is in transit and runs to more than one page starts over each time; no test exercises it.
23. **Reference-relay timestamps.** The relay already stamped events when it sequenced them, but a witness's frontier was computed from the relay's clock rather than read off the events, so a relay that refreshed times would have changed nothing. The frontier is now the newest time on the events processed, the rest of the network's included, and `Relay.timeOnDelivery` shows the failure the requirement prevents: a witness 28 hours behind after an outage, or 30 behind a slow relay, reads as current, and Bob misses the deadline (`witness.test.ts` "not the reference relay…"; mutation "relay refreshes time on replay"). A relay passing on PDS-chosen times is not modeled; since a frontier is the newest time processed, one event stamped ahead would move it for every account at that witness.

Findings from Astra's third review (where a witness's history starts, and `since`):

24. **The gap before a witness's history didn't bound what it hides.** It ran through the revision before the first one the witness held, which fails as a stream gap's resync revision did (finding 21): Bob's phone is at revision R; his PDS publishes an impostor, which Carol's app accepts, then replays R through a relay that doesn't check revisions; Bob's witness is rebuilt after the replay window and starts at R, so its gap ends at R − 1, Bob resumes from R, and nothing is raised (`witness.test.ts` "an impostor published and the original revision replayed, then Bob's witness rebuilt…"; also a restore onto a new application's witness started after the replay). **Rule changed:** the missing interval runs through `REV_ALLOWANCE` past the relay time at which the witness started following the account, or its starting revision if higher; a cursor moves past it only to the starting revision; it is served to every cursor it reaches. The prototype follows all three (mutations "rebuild gap ends at the starting revision", "rebuild gap served only after the cursor", and "cursor moves to the rebuild gap's end": with the cursor at the gap's end, an impostor relayed just after the rebuild, inside the interval, is never read). A witness meeting an account after a stream gap uses the time it resumed. Walks now rebuild witnesses (`witnessRebuild`). The cost, as for stream gaps: a rebuild or a new witness warns every user it serves whose cursor its interval reaches. The prototype keeps an older choice: a late witness reports this gap even for an account whose first event came after it started.
25. **Roots can't show that no commit came between** (Decisions on witnessed state). An honest PDS adds a record, deletes it, then makes another change; the relay drops the add and the delete; the next published commit still inverts to the witness's root, so the add sat between two consecutive reconstructions, and a client served it (a delayed response, say) raised a false `unrelayed-commit` alarm ("an honest PDS adds a record and deletes it…"). The unchanged-data exemption (finding 16) didn't help: the add changed records. **Rule changed:** two reconstructions are consecutive only if the later is a `#commit` whose `since` names the earlier's revision and whose operations invert to the earlier's root, and the exemption is gone; a `#commit` whose `since` names another revision records a gap before it, but is itself reconstructed whenever its operations invert to the witness's state, with no fetch. The prototype models `since` (an honest PDS's is its true previous revision) and follows both parts (mutations "consecutiveness ignores since", "a since mismatch makes the commit itself a gap", and "consecutiveness ignores root (since only)", caught through operations that don't reach the commit's root: in the prototype, operations that apply to the witness's state already imply root continuity). The gap before runs from just after the witness's latest revision through the revision before the commit, not through the revision `since` names, which the PDS may misstate. A dropped commit that changes nothing now lies in that gap the same way. A malicious PDS that hides a commit and names the last relayed revision still alarms; one that misstates `since` breaks the pair and avoids the alarm, as a `#sync` can (finding 15), and the hidden commit is still never accepted.
26. **A starting commit below the installation's cursor.** The bounded gap (finding 24) covers revisions above the cursor, but nothing covered those between a starting revision below the cursor and the cursor itself. Bob's phone is at r; his PDS replays an earlier r0 < r through a relay that doesn't check revisions; his witness is rebuilt after the replay window and starts at r0, which it can't tell is below anything it held; the PDS then publishes an impostor at r0 < ri < r, which the rebuilt witness reconstructs (ri is above r0, so no non-increasing alarm) and Carol, on the same application, accepts. Bob read from r, so the impostor lay below his cursor and the goal check flagged him (`witness.test.ts` "an earlier revision replayed before the rebuild…", recorded first as a FINDING). **Rule changed:** an installation whose cursor was set by a commit the relay sequenced before the witness started following the account, and is above the revision the witness's history starts at, or at it with a different commit, raises an integrity alarm with the starting commit as proof and records a gap there; it keeps the relay time of the commit that set its cursor, and the witness reports when it started following. The prototype implements it, with the gap running from the starting revision through the cursor, which covers the later impostor; also for an impostor republished below the cursor before the rebuild, and a different commit at the cursor's own revision (mutations "starting commit below the cursor raises no alarm", "a different starting commit at the cursor raises no alarm"). The qualifier matters: applied to every cursor, the check false-alarmed on an honest restore onto another application's witness that started following the account just before the backup's cursor commit, whose start gap reaches that cursor (mutation "starting-commit check applied to every cursor"; the invariant monitor flags the false alarm too). The prototype compares relay times strictly, so a cursor commit sequenced in the same instant the witness started counts as after it; sequence numbers would be exact. It applies the check to every account an installation follows from a cursor, pinned ones included, not only its own.

Observations: because the single-root rule declines unlinked devices and a PDS cannot sign approvals, every first-contact impostor the PDS gets accepted has to be published as a reset of the account, so the user's installations also see their own record deleted; watching every commit matters most for resets that are quickly undone and for accounts with no device yet. A PDS can create own-account gaps at will (a replaced root, a withheld fetch); since gaps only warn and each is acknowledgeable, a run of harmless gaps can train a user to acknowledge the one that hides an impostor. Witnesses could tell withholding from failure by asking one another whether they reconstructed the commit; a gap another honest witness filled is withholding, which could alarm (question 2). The own-added notice, not an alarm, is what a device approved with a copied key produces, as before.

#### Witness traces

`traces-witness/` holds shared-view witness walks, regenerated and checked like the others by `test/traces.test.ts`, in the same format as `traces-inviters/` with `"policy": "witness"`. Two differences: ops may include a brief impostor, an add of a device that replaces every device of an account (deletes, then the add) in one step and, in a later step, its deletion with the earlier devices added back; and each step adds `ownAlarms`, the viewer's own-account bindings it has alarmed about as unrecognised so far. With an honest relay and witness, and installations syncing after every commit, the viewer's acceptance, holds, standing, and authorizations should match the inviters replay exactly; `ownAlarms` checks that the viewer alarms on its own account's brief impostors even after they are deleted.

### What it does not model

- Cryptographic security against a symbolic attacker: the simulations test trust logic, not secrecy proofs.
- Real atproto repos: an enumeration is a whole record map at a signed commit, with no MST, CIDs, or DID documents.
- Real Spaces credentials: a virtual-time expiry gated on a live session and membership, with no delegation tokens or HTTP Message Signatures.
- Platforms: resource budgets, background issuance on phones, key storage, and removal on real PDSes ([TODO-16](../TODOs.md#todo-16)).
- Malicious application code, and blobs.
- Under the witness policy: real firehose frames, CAR blocks and MST inversion (a reconstructed state is the whole public repo), the relay's own clock (its times are world time; witness clock offsets are modeled), a relay passing on PDS-chosen event times, time in transit for anything but history answers, and the relay's own repo serving.

## Running the checks

`npm test` runs the crypto vectors, the forty-two scenarios, random walks in two modes under each of the three policies, focused tests (publication, archive reading and key loss, host integrity and membership, multiple spaces, backends, key rotation and migration, imports, network lag, the disclosure check, starting over after total device loss, the inviters policy, the witness policy), a check that the three sets of trace fixtures still regenerate, and every UX figure's panel expectations. Longer walks: `NBD_WALKS=300 NBD_STEPS=40 npx vitest run test/fuzz.test.ts`. `node test/mutate.mjs --all` breaks one trust rule at a time and reports whether any test notices; every mutation should be caught. `npm run build` produces a static site in `dist/`.

## Layout

- `src/protocol/`: the client, free of UI code. `crypto.ts` composes the `nbd-hpke-v1` HPKE profile from noble primitives, checked against the RFC 9180 test vector for that suite; `trust.ts` ports `SpecClient` (first use, approvals with the live-binding rule, revocation, holds); `grants.ts` implements G1–G5 and A1–A7, including archive mode; `publish.ts` and `installation.ts` implement the publication state machine P1–P8; `installation.ts` runs the sync loop and pins every member of its spaces (a lazy mode exists only to show what eager pinning prevents), and under the witness policy follows each account through its trusted witness; `witness.ts` holds the witness client state (cursors, coverage, gaps) and the witness interface.
- `src/world/`: the emulated PDS (signed, timestamped commits, create-only app sessions, one-off delete authorizations, key rotation, migration, and under the witness policy what it sends the relay and serves witnesses), `relay.ts` (the reference relay, witnesses, and a PDS-run rogue witness), Spaces host (membership, configuration, short-lived credentials, and tampering for tests), `adversary.ts` (a malicious PDS withholding commits from, or signing forged snapshots for, chosen installations), and `World`, which adds the clock, per-installation network lag, write faults, backups, provenance for the goal check, and user and attacker actions.
- `src/sim/`: narrated scenarios with expectations; the invariant monitor; the goal-level disclosure check; the witness policy's detection check (`detection.ts`); and `fuzz.ts`, random walks with shrinking over two spaces and user, attacker (takeover, devices added with the password, copied keys, recreated records), network (lag, offline, write faults), clock (backward moves), host (tampering, membership changes), infrastructure (key rotation, migration), and malicious-PDS (substitution, hidden reset, forks, rollback) actions.
- `traces/`: shared-view walks under the baseline policy, recorded as public-repo operations plus the viewer's decisions after each step. `model/test_traces.py` replays them through `SpecClient`, so the prototype and the model must agree exactly. `traces-inviters/` does the same for the default policy ([format](#inviters-traces)), and `traces-witness/` for the witness policy ([format](#witness-traces)). Regenerate all three with `NBD_WRITE_TRACES=1 npx vitest run test/traces.test.ts`.
- `src/ux/`: the UX app. `model.ts` turns an installation's state into screen models, `screens.tsx` and `frames.tsx` draw them, `copy.ts` quotes the flow documents, `figures/` holds the storyboard scripts, and `wall.tsx` is the device wall. `scripts/capture.mjs` screenshots the figures with Playwright.
- `src/ui/`: a store over one simulation (`sim.ts`), node cards that each render one installation's own state with the [Paranoid flow](../ux-flows/paranoid.md) copy, and the inspector (trust matrix, key holders, repos, log).

## Simplifications

- A repo enumeration is the whole record map at a signed commit: no MST, CIDs, or DID documents. Key rotation updates a registry of current keys; commits under an old key go unverified rather than being checked against DID history.
- Credentials are a virtual-time expiry gated on a live session and eligible membership; no delegation tokens or HTTP signatures.
- Installations sync whenever the world settles while they are online. Network lag is per installation: it reads every repo as it was that many hours ago. Host reads are never delayed.
- Keys and nonces come from a seeded generator so runs replay. Never do this outside a simulation.
- Records only; no blobs.
