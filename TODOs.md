# PEEP: Remaining Work

Baseline design decisions are resolved. Implementation, interoperability, and independent security validation remain outstanding. IDs are retained for existing references.

## Implementation and validation

<a id="todo-03"></a>
### 03: Spaces integration

Allocate production namespaces and implement concrete Lexicon/XRPC mappings for the [host contract](core.md#trusted-host-state). Validate authorization, historical storage, migration, and creation-fixed configuration fields, including the key commitment, against the selected Spaces revision; expose required reads without granting administrative powers.

<a id="todo-08"></a>
### 08: Recovery and backup

Implement and validate the application's [protected backup/pairing container](device-enrollment.md#backup-and-transfer), including ownership, encryption/KDF, atomic import, corruption, rollback limits, and recoverability. Design a process for [total device loss](device-enrollment.md#total-device-loss): today a user who loses every installation and backup must be re-verified, cannot revoke the lost bindings, and loses keys only those installations held.

<a id="todo-09"></a>
### 09: Publication and sync

Implement and test [grant publication and auditing](audit.md), creator-first scheduling, and the specified [key-request records](core.md#key-requests) over Spaces repo writes/direct sync, including keyless discovery, bounded retries, and disposable request retention. Map the records to production Lexicons under [TODO-03](#todo-03).

<a id="todo-10"></a>
### 10: Interoperability and security

Publish byte-exact positive/negative vectors, cross-check independent implementations, and obtain independent protocol/cryptographic review. Track coverage in [validation cases](#validation-cases).

<a id="todo-12"></a>
### 12: Platforms

Validate Ed25519/X25519 operations, installation identity, storage, pairing, restore, and independent-app behavior against [platform constraints](device-enrollment.md#platform-notes), including browser origin/profile isolation and state loss.

<a id="todo-14"></a>
### 14: Verification sessions

Map [verification session](device-enrollment.md#independent-verification) messages to a concrete relay, including `pin` session discovery by responder account, under [TODO-03](#todo-03). Fix `peep-verify-v1` SPAKE2 MHF parameters, publish transcript vectors, and validate single-use persistence, expiry, and session UI on each [platform](#todo-12).

<a id="todo-16"></a>
### 16: Removing PDS access from the app

Today a user who removes a device must also remove its access at their PDS themselves ([ending access](core.md#ending-access)). An application could do this for them, which would need a way to identify the removed device's PDS session and PDS support for ending another session. Neither exists today, and PEEP does not specify a mapping from device bindings to sessions.

<a id="todo-15"></a>
### 15: Background issuance and trust sync

Map [own-device trust sync](device-enrollment.md#own-device-trust-sync) messages to a confidential transport under [TODO-03](#todo-03) that retains the latest snapshot per source for offline installations, and publish vectors. Validate background processing of [key requests](core.md#distribution-scheduling) and push wake-up on each [platform](#todo-12), including iOS notification extensions, key availability while locked, and member prompts when no grant arrives.

## Deferred extensions

- **02:** Cross-user verification attestations. Verifying parties that cannot run a session, such as published fingerprints for unattended devices.
- **06:** Expiring approval needs reliable clocks and renewal by approvers that stop renewing withdrawn devices. Per-grant approval needs an online trusted approver, issuer nonce, exact binding, deadline, and replay protection. A fresh response alone proves neither current authority nor consent; any delay bound must state its assumptions.
- **08:** Cross-application backup portability.

<a id="todo-13"></a>
### 13: Authenticated streaming

Large media, seeking, or early playback needs a separate versioned format authenticating chunk order/count, total length, object identity, and final manifest. Test truncation and cross-object substitution; [Format 1](core.md#encrypted-blobs) requires bounded whole-file authentication.

## Validation cases

Each row requires implementation evidence; prose/link checks do not satisfy it. Conformance vectors MUST include exact inputs, ordered observations, starting local state, expected result/reason, durable state changes, and permitted network/key-release actions. Cross-implementation comparisons use the same local history; different observed histories need not produce identical authorization decisions.

| Area | Required cases |
| --- | --- |
| Encoding and cryptography | Fingerprints, verification invite/secret/session encodings and SPAKE2 transcript, all signing domains, CID/CBOR normalization, grant headers/manifests, HPKE suites/lengths, commitments, record/blob AAD and nonce separation; malformed/duplicate/unknown fields, signatures/points/all-zero KEM inputs, altered contexts, account/space/location substitution, no suite fallback, finite limits, full authentication before plaintext. |
| Format 1 framing and padding | Use `com.example.peep.envelope` consistently and reject other envelope types. Records and blobs use the same CBOR frame of two byte strings with empty or nonempty zero-filled padding; all readers support both. Round-trip binary files (including empty files and trailing zero bytes) and normalized record maps; exercise CBOR length boundaries and default/custom size buckets. Reject wrong arity/types, nonzero padding, non-normalized encoding, trailing bytes, truncated or oversized declared lengths, and unframed content; no fallback. Authenticate before frame parsing or content release, preserve record schema checks, and enforce padded ciphertext/full-blob limits before allocation. Ciphertext length is frame length plus 16; blob CID/size cover the entire encrypted envelope. No outer original-length field; counts, timing, blob relationships, and padded sizes remain visible. Grant plaintexts are unchanged. Include byte-exact positive/negative vectors and independent review. |
| Default padding | Minimum 256-byte ciphertext and increasing power-of-two buckets include both byte-string headers, the array header, payload, padding, and 16-byte tag. Select the smallest attainable bucket; skip header-length gaps (a 212-byte payload cannot produce 256-byte ciphertext and uses 512 with 278 padding bytes). Cover empty payloads, exact buckets, every header boundary, and bounded arithmetic before allocation. Check outer record/envelope and transport limits: use empty padding when no bucket fits, reject if even that exceeds a limit. Readers accept other valid sizes. Shared defaults reduce only padding-specific fingerprints; visible collections and metadata remain exposed. |
| Blob references | After record authentication/schema validation, check nested maps/arrays for complete blob references matching authenticated envelope entries, including CID, MIME type, and size. Reject missing references and same-CID metadata mismatches before content use; ordinary CID links do not require blob entries, and extra envelope entries remain permitted. Modified/reordered outer lists fail AAD authentication; original file metadata stays inside encrypted content. |
| Locally current state | Withheld newer approvals, revocations, membership, or configuration leave clients using their latest authenticated local state without claiming freshness. Reordered delivery cannot regress revisions or clear learned withdrawals; missing required evidence blocks affected operations. Apply to grant/retry/direct checks and current verification policy on first key acceptance; historical authorization still uses historical evidence. Newer learned state takes effect under existing rules. |
| Host authority | Authenticate current/historical membership/configuration through migration; credentials/writer lists are not membership or device evidence. No creator signature or issuer appointment. Any eligible enrolled holder may grant the space key, including to members admitted after content was posted; reject known removed issuers/recipients. Admission cannot bypass verified-only: unverified bindings remain blocked, while verified bindings are eligible when other checks pass. `deviceVerification` is fixed at creation: the host rejects changes, and clients reject a configuration with a different policy than first observed as `INVALID`, keep the last valid configuration, and raise an integrity alarm, including after restart, migration, and restore; an administrator's PDS cannot relax a verified-only space. |
| Membership visibility | Authenticated additions, removals, and readmissions become visible when learned; cover offline reconciliation and affected accounts. Retained-history access is discoverable, for example in space information. Inspect grants to other members with exact bindings, issuer, membership/policy evidence, and gaps. Unexpected host-authorized membership is not a protocol violation when other checks pass. Notices add no approval gate or pre-disclosure guarantee. |
| Verification | Initial PDS substitution versus independently verified rejection; changed pins, downgrades, exact DID/device/both-key binding in the session transcript. One session verifies both directions for `qr`, `link`, and `pin`. Relay substitution of either share, binding, or confirmation fails; a racing attacker consumes the session and Bob's attempt fails visibly. Single use under crash/restart before and after V2/V3 persistence; expiry; wrong `expectedResponder` discarded without consuming; no second responder attempt; no automatic retry. Failures change no trust state; success with keys differing from a pin records a dispute. Self-signatures/PDS/relay delivery of the secret insufficient; mismatches block until resolution. Reuse across spaces/lifecycle without repeat OOB or bypassing space authorization. |
| TOFU key changes | Policy selects trust per space: TOFU spaces accept unapproved new/changed bindings as key changes even for accounts with verified bindings, never under verified-only and never for revoked bindings; verified-only spaces require verified-rooted approval or independent verification, and unapproved changes to a verified binding record disputes that block only there. Accepting a TOFU key change never replaces, downgrades, or clears a verified pin, which stays in effect for verified-only spaces; TOFU-rooted approvals never count in verified-only spaces. Three-party case: Alice verified Bob, Carol pinned a substituted Bob device by TOFU and grants it; the space key is exposed, and no verified-status gate applies in TOFU spaces. Record superseded pins, surface every accepted change to the affected account's peers, add no approval gate, and label resulting grants `tofu`. Approvals from withdrawn signers do not establish trust but may fall back to a key change where permitted. Re-pin after own state loss only for TOFU spaces and with the loss reported. Verifying keys that differ from a TOFU pin replaces it and flags earlier exchanges. |
| Own-device trust sync | Snapshots from accepted unwithdrawn own installations only; reject other accounts, unknown or withdrawn sources, wrong recipient key, replayed or lower sequences, and altered headers. `verified` upgrades exact TOFU pins and satisfies verified-only; `tofu` never upgrades and creates pins that apply only in TOFU spaces; a differing `verified` entry or a `disputed` entry records a dispute, while a differing `tofu` entry is a TOFU key change for TOFU spaces and leaves any verified pin in effect for verified-only spaces. Omission never removes trust. Retain decisions applied before source withdrawal. Never sent across accounts, published in space repos, or included in evidence. |
| Approvals | Same-account additions rooted in TOFU/verified bindings, offline approver reuse, retained private provenance; reject cross-account substitution, missing/unanchored/cyclic approval, unjustified promotion, and another issuer's status/grant as verification. Approvals from not-yet-accepted signers stay pending and apply once the signer is accepted; out-of-order delivery yields the same accepted set; withheld approvals delay but never remove devices; approvals never revive revoked bindings. Withdrawn approvers cannot establish new bindings through backdated or unaccepted intermediate approvals. Every accepted, unwithdrawn device of a member account is eligible in every space the account belongs to; no per-space selection exists. Linking requires authenticated pairing plus confirmation of adding a device, with a warning that it can read all the account's spaces; a device-reported name is not treated as authenticated. |
| Upgrades and policy | Exact-binding upgrade affects future local decisions only; preserve prior grant status and derived provenance, never revive revocations. Verified-only applies to granting and accepting keys, retries, and direct delivery; issuer and recipient each verify the other locally. One eligible issuer suffices when both checks pass. Reject a TOFU issuer even if the recipient is verified, and a TOFU recipient even if the issuer is verified; valid signatures, reported recipient trust, and successful decryption cannot bypass these checks. Missing configuration never permits fallback; verification upgrades cannot repair disclosure or invalidate valid archives. First key acceptance from an archive still verifies the issuer; upgrades preserve prior valid acceptances and historical grant validity. TOFU-space interfaces show no verified status or verification action. |
| Withdrawals | Same-account peer/self, compromised accepted signer withdrawing peers, invalid/cross-account/unknown signers, cutoffs for withdrawn signers, modified target/scope. Preserve across deletion, replay, restore, future spaces. Previously accepted bindings survive approver withdrawal subject to their own withdrawal. Relays use local trust; withheld updates never imply bounded freshness. |
| Revocation authority | Self-revocation, mutual/longer revocations, open chains, and arbitrary outgoing statements use independent per-statement checks. Permute delivery for a fixed device set accepted before any withdrawal: all valid statements take effect. After signer withdrawal, accept revocations of targets with Aₘ(target) < Wₘ(signer) in the same mode, including newly signed statements long afterward; reject targets accepted at/after the cutoff and known never-accepted targets. Unknown or incomparable positions remain incomplete. Active signers may revoke not-yet-accepted targets without establishing trust in them. Unknown/unaccepted/cross-account signers and invalid signatures gain no authority. Cover all older devices withdrawn, fresh replacement recovery, and clients permanently disagreeing when replacement acceptance straddles the signer's locally observed withdrawal. No approval or grant authority is restored. Cross-mode case: Alice independently verified Bob's phone; in a TOFU space Bob's PDS introduces a binding Alice accepts as a TOFU key change, and it revokes the phone. The phone is withdrawn in Alice's TOFU spaces only, stays eligible in her verified-only spaces, and later independent verification of it still counts there. If Alice later verifies the attacker's signer, the revocation takes effect in verified mode from that point, never backdated. A verified signer's revocation takes effect in both modes. |
| Ending access | Space creation configures a read policy requiring delegation tokens; conforming applications never create one with a public read policy. Member removal ends credential issuance and access within one credential lifetime, sooner with `notifyCredentialRevoked`. Device revocation alone leaves Spaces access in place while the device holds a PDS session; removing its PDS access ends it within one credential lifetime. Every device-removal path, including own-account notices, tells the user to remove PDS access and never claims immediate cutoff. Shared application backends keep access through other members' sessions. |
| Space key | The creator generates a fresh random key and key ID, stores it durably before creation, and supplies `keyId`/`commitment` in the creating configuration. Grants and acceptance match the configuration's key ID and commitment; reject mismatches. The host rejects changes to `keyId`/`commitment`; clients reject a configuration whose values differ from those first observed as `INVALID`, keep the last valid configuration, and raise an integrity alarm, including after restart, migration, and restore. Removals, revocations, and suspected compromise block new grants but never change the key; removal and revocation notices never claim cryptographic exclusion, and removal flows neither default to nor prompt space replacement. A replacement space has a fresh key and reuses device trust without carrying content; republished content is the republisher's. Writers without the key retain drafts until a grant arrives. Loss of every key copy and backup makes the space unreadable and unwritable. |
| Distribution scheduling | Request-driven delivery: devices request keys for spaces they open; holders answer after randomized backoff; unrequested grants only to devices known to use the space, including the creator's prompt grants to its own same-application installations; no unrequested grants to other devices. Concurrent helpers, partial repo views, retries, and duplicates retain normal publication checks. Existing grants with unverified issuers, missing evidence, or bad ciphertext cannot permanently suppress alternatives. Requests usable without content keys remain non-authoritative, bounded hints; no exclusive issuer or complete-coverage claim. |
| Key requests | Publish unencrypted signed requests in the requester's space repo; discover through normal authenticated sync, notifications, offline catch-up, and periodic reconciliation without content keys. Reject bad schema/signature and account/space/location substitution; validate the configuration and the recipient binding's acceptance independently. A valid self-signed request cannot seed trust or bypass withdrawals, verification policy, or grant publication/acceptance. Any/preferred issuers and requesting an alternative after an unusable grant; preferred issuer has no exclusive authority. Exact retries reuse bytes/identity; semantic deduplication, per-account bounds, randomized backoff, and reconsideration after authorization/key changes. Delete satisfied/abandoned/obsolete hints without audit gaps, evidence pruning, or a claim of receipt; exclude requests from evidence manifests. Suppression, denied access, and offline holders can prevent delivery; no delivery is promised. |
| Evidence and archives | Exact issuer/recipient bindings and approval paths, host decisions, actual retained bytes when source PDS withholds; no private OOB/cross-space provenance leakage or inherited verification. Historical reading after removals/revocations still checks signatures/bindings/evidence/commitment. Missing required evidence blocks; historical uncertainty alone need not block valid decryption but timestamps do not prove ordering. Archives never restore authority or access. |
| Publication retries | Durable bytes/identity before release, evidence-first upload, crashes before/after publication/ack, identical retries give one record. Changed bytes are new issuance. Recheck both parties/policy/withdrawals/evidence on retries/direct delivery, even after acknowledgment. Missing acknowledgment leaves exposure uncertain and forbids direct forwarding; stopped retries preserve published audit records. |
| Own-account device notices | Every own installation except the approver notifies the user of each new or removed own binding, including those approved by another own installation, learned from an approval, device record, revocation, another issuer's grant, or trust sync. A grant in another issuer's repo triggers the notice when the account's own PDS hides the record. One notice per binding across all spaces. Removal from the notice revokes without rotating and offers space replacement, since an unrecognized device suggests compromise. Notices are not integrity alarms and add no gate; existing alarms for bindings no own installation approved remain. Other members get no required notice for approved changes. |
| Auditing | TOFU substitution, at first contact or through a TOFU key change, detected promptly through honest issuer repos and retained own history despite source withholding; alarms for grants to unapproved own bindings and for unaccepted approvals/device records in the local account's public repo, including when the account's PDS hides them from its own reads. Forged audit signatures, stale formerly authorized versus never-authorized keys, legitimate revisions, suppression/collusion, unknown history, observations versus grants. Signature attributes statement, not PDS misconduct or decryption. Review metadata and transferable-signature privacy. |
| Retention and sync | Indefinite grants, exact evidence, approvals, and revocations; preserve through migration/revocation/membership/restore. Host discovery plus retained participants, former repos while authorized, audit before key delivery, interrupted checkpoints/gaps, expiry/deletion/unavailable history. Offline catch-up, retained local auditing after removal without promised further access; no all-grants-seen claim. Background gaps neither bypass grant checks nor block unrelated work. |
| Recovery/transfer | Surviving approval or independent helper verification of fresh keys, one eligible holder can restore spaces whose keys it holds without transferring trust to others. Verified-only spaces reject PDS-only replacement; TOFU spaces may accept it only as a recorded, surfaced TOFU key change, even where the client holds verified bindings for the account. Reject revived withdrawals or re-invitation history reset. Authenticated/confidential keys plus pins/provenance/order/approvals/withdrawals and first-observed policies; older imports preserve newer known state. Undetectable backup rollback retains its stated limits. Missing/incomparable history cannot invent prior acceptance; key-only restore cannot recreate trust; all copies lost means plaintext lost. |

### Procedure and transition coverage

| Procedure | Required mapping and additional cases |
| --- | --- |
| [G1–G5: exchange authorization](core.md#grant-authorization) | Host authority, verification, approvals, withdrawals, and locally current state. Both local roles; known denial versus missing evidence; valid readmission restores eligibility but never a revoked binding; no release before `OK`; authorization changes between validation and release. |
| [A1–A7: grant acceptance](core.md#grant-acceptance) | Encoding, policy, evidence/archives, and the space key. No decryption before required checks; compare the recipient's entire binding, including a substituted signing key with the same encryption key/ID. Both modes reject an ineligible recorded membership decision even after readmission. Missing mandatory evidence blocks; uncertainty about issuance timing or the issuer's then-known state alone need not block an archive. Later revocation alone does not invalidate history. A5 applies the space policy in both modes; A7 rechecks newly learned state. No trust promotion. |
| [D1–D3: approvals](device-enrollment.md#approval-validation) | Approvals, withdrawals, and recovery. Pending approvals apply atomically once their signer is accepted; accepted bindings survive their approver's later withdrawal without accepting new approvals by that signer; approvals of withdrawn targets have no effect; invalid input cannot erase state. |
| [R1–R4: revocations](device-enrollment.md#revocation-processing) | Withdrawals, cutoff authority, recovery, and bounded validation. R1 replays preserve accepted statements without moving Aₘ/Wₘ or reauthorizing the signer. Distinguish known never-accepted bindings from missing acceptance history, and unwithdrawn status from missing withdrawal history. R3 uses the target's first acceptance and signer's first accepted withdrawal; inactive receipt cannot backdate W, later revocations cannot advance it, and timestamps/other issuers' histories cannot replace local ordering. R2–R4 atomically check authority and retain the statement/withdrawal/cutoff, including races with other withdrawals. An already withdrawn or unknown-history target never receives an invented later cutoff. Preserve accepted revocations despite later signer withdrawal. Run R1–R4 separately per trust mode with separate Aₘ/Wₘ positions; a TOFU-only signer never sets a `verified` cutoff. Re-evaluate incomplete candidates when evidence arrives; bounded/resumed work never suppresses independently valid withdrawals or invents authority. |
| [P1–P8: publication](audit.md#publication) | Publication retries, evidence, and retention/sync. Every transition, partial uploads, acknowledgment loss, absent/different repo bytes, reauthorization before each release, and late acknowledgment after stopping. Stopping preserves prior exposure facts. |
