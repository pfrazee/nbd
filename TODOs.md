# PEEP: Remaining Work

The baseline is drafted against the [security goals](security-goals.md), a Signal-level threat model: trust on first use, approvals afterwards, and a hold for clients that knew an account before its reset. The goals and the design still need independent review. Implementation, interoperability, and independent security validation also remain outstanding. IDs are retained for existing references.

## Implementation and validation

<a id="todo-08"></a>
### 08: Recovery and backup

Implement and validate the application's [protected backup/pairing container](device-enrollment.md#backup-and-transfer), including ownership, encryption/KDF, atomic import, corruption, rollback limits, and recoverability. Choose `REENROLL_HOLD` for [re-enrollment](device-enrollment.md#re-enrollment) (72 hours is a placeholder), balancing how quickly a user without devices regains access against how long an account holder has to notice a takeover. Design an optional hold-free mechanism that a PDS cannot exercise alone, such as an offline recovery key that can approve devices after every device is revoked, or social recovery through other members.

<a id="todo-16"></a>
### 16: Device removal on existing PDSes

Removing a device takes two steps at the account's PDS: deleting its device record, which [revokes](device-enrollment.md#device-revocations) it, and ending its session ([ending access](core.md#ending-access)). PEEP cannot change PDS behavior, so the two stay separate unless PDSes later add a mapping from a device record to the session that created it. Validate the PDS behavior PEEP relies on as it exists: OAuth permission enforcement for create-only sessions across PDS implementations, including `putRecord` requiring `update` and per-operation checks in `applyWrites`; the separate delete authorization flow; device records surviving migration; and authenticated proofs. Proofs come only from the sync layer: record-level reads (`com.atproto.repo.getRecord`, `listRecords`) carry no commit or revision. Presence uses `com.atproto.sync.getRecord` inclusion proofs; absence uses enumeration of the repo at a verified commit. A full export of a large repo is costly for clients that track many accounts, so measure that cost, and specify incremental maintenance from verified commit events or `getRepo` diffs, including the adjacent MST nodes the repository spec requires to verify deletions. Device records form one contiguous key range in the MST, so consider proposing an atproto endpoint that returns a verifiable enumeration of one collection.

### 17: Executable trust model

An executable model of [local trust](device-enrollment.md#local-trust) is in [`model/`](model/README.md), with adversarial cases and a mutation check. It corrected the single-root rule, persisted approval-derived acceptance independently of the current repo, and bound holds to their exact candidate. Its [variant comparison](model/COMPARISON.md) records the anchor and witness designs PEEP tried before adopting the Signal-level goals. The model assumes one shared, current view of every repo; partial views, delayed observations, and divergent installations need the prototype in [TODO-18](#todo-18).

## Deferred extensions

- **02:** Verified-only spaces. Independent device verification would prevent first-contact PDS key substitution, but only when every exchange in a space requires it, so it would be a space policy fixed at creation in configuration; current clients reject such a configuration because decoding rejects unknown fields. A design must keep TOFU acceptance from weakening verified trust: first-use pins must not stand in for verification, and devices whose trust rests only on a first-use pin must not approve devices in verified-only spaces, which needs separate acceptance per mode. Interfaces must not show verified status in TOFU spaces. It also needs a verification ceremony (earlier drafts used single-use SPAKE2 sessions over QR, link, and PIN channels), dispute handling for changed verified bindings, and a way to carry verifications to a user's own installations. Cross-user verification attestations, such as published fingerprints for unattended devices, belong here.
- **06:** Expiring approval needs reliable clocks and renewal by approvers that stop renewing revoked devices. Per-grant approval needs an online trusted approver, issuer nonce, exact binding, deadline, and replay protection. A fresh response alone proves neither current authority nor consent; any delay bound must state its assumptions.
- **08:** Cross-application backup portability.

<a id="todo-13"></a>
### 13: Authenticated streaming

Large media, seeking, or early playback needs a separate versioned format authenticating chunk order/count, total length, object identity, and final manifest. Test truncation and cross-object substitution; [Format 1](core.md#encrypted-blobs) requires bounded whole-file authentication.

## Validation cases

Each row requires implementation evidence; prose/link checks do not satisfy it. Conformance vectors MUST include exact inputs, ordered observations, starting local state, expected result/reason, durable state changes, and permitted network/key-release actions. Cross-implementation comparisons use the same local history; different observed histories need not produce identical authorization decisions.

| Area | Required cases |
| --- | --- |
| Encoding and cryptography | Fingerprints, all signing domains, CID/CBOR normalization, grant headers/manifests, HPKE suites/lengths, commitments, record/blob AAD and nonce separation; malformed/duplicate/unknown fields, signatures/points/all-zero KEM inputs, altered contexts, account/space/location substitution, no suite fallback, finite limits, full authentication before plaintext. |
| Format 1 framing and padding | Use `com.example.peep.envelope` consistently and reject other envelope types. Records and blobs use the same CBOR frame of two byte strings with empty or nonempty zero-filled padding; all readers support both. Round-trip binary files (including empty files and trailing zero bytes) and normalized record maps; exercise CBOR length boundaries and default/custom size buckets. Reject wrong arity/types, nonzero padding, non-normalized encoding, trailing bytes, truncated or oversized declared lengths, and unframed content; no fallback. Authenticate before frame parsing or content release, preserve record schema checks, and enforce padded ciphertext/full-blob limits before allocation. Ciphertext length is frame length plus 16; blob CID/size cover the entire encrypted envelope. No outer original-length field; counts, timing, blob relationships, and padded sizes remain visible. Grant plaintexts are unchanged. Include byte-exact positive/negative vectors and independent review. |
| Default padding | Minimum 256-byte ciphertext and increasing power-of-two buckets include both byte-string headers, the array header, payload, padding, and 16-byte tag. Select the smallest attainable bucket; skip header-length gaps (a 212-byte payload cannot produce 256-byte ciphertext and uses 512 with 278 padding bytes). Cover empty payloads, exact buckets, every header boundary, and bounded arithmetic before allocation. Check outer record/envelope and transport limits: use empty padding when no bucket fits, reject if even that exceeds a limit. Readers accept other valid sizes. Shared defaults reduce only padding-specific fingerprints; visible collections and metadata remain exposed. |
| Blob references | After record authentication/schema validation, check nested maps/arrays for complete blob references matching authenticated envelope entries, including CID, MIME type, and size. Reject missing references and same-CID metadata mismatches before content use; ordinary CID links do not require blob entries, and extra envelope entries remain permitted. Modified/reordered outer lists fail AAD authentication; original file metadata stays inside encrypted content. |
| Locally current state | Withheld newer approvals, revocations, membership, or configuration leave clients using their latest authenticated local state without claiming freshness. Reordered delivery cannot regress revisions or clear learned revocations; missing required evidence blocks affected operations. Apply to grant/retry/direct checks and issuer acceptance on first key acceptance; historical authorization still uses historical evidence. Newer learned state takes effect under existing rules. |
| Host authority | Authenticate current/historical membership/configuration through migration; credentials/writer lists are not membership or device evidence. No creator signature or issuer appointment. Any eligible enrolled holder may grant the space key, including to members admitted after content was posted; reject known removed issuers/recipients. Configurations carrying unknown fields, including a future verification policy, are rejected rather than treated as TOFU. |
| Membership visibility | Authenticated additions, removals, and readmissions become visible when learned; cover offline reconciliation and affected accounts. Retained-history access is discoverable, for example in space information. Inspect grants to other members with exact bindings, issuer, membership evidence, and gaps. Unexpected host-authorized membership is not a protocol violation when other checks pass. Notices add no approval gate or pre-disclosure guarantee. |
| Trust on first use | First use and approvals. First use enumerates the repo and accepts the present records account-wide only under the single-root rule, ignoring roots that reach only deleted devices; two live roots decline and surface the account. Cover first seeing a later device. Initial substitution, including root theft with an approval signed by the attacker's own device and a new contact meeting an account just after a takeover, is accepted and detected only through auditing, never prevented; assert these as documented exposures. While any accepted binding survives, reject every unapproved binding of the account with no user override; such bindings stay incomplete and are surfaced. Approval-derived acceptance persists when the approval record is later deleted, and across export and import. Never accept revoked bindings or replace pins. Re-pin after own state loss only with the loss reported. Issuer and recipient each check the other locally; reported trust, valid signatures, and successful decryption cannot substitute for acceptance. Installations of one account pin independently after pairing. Trust is reused across spaces and survives space lifecycles. |
| Approvals | Same-account additions rooted in accepted bindings, offline approver reuse, retained approval evidence; reject cross-account substitution, missing/unanchored/cyclic approval, and another issuer's status or grant as acceptance. Approvals and targets count only when proven present in the account's repo; relayed copies never do. Approvals from not-yet-accepted signers stay pending and apply once the signer is accepted; out-of-order delivery yields the same accepted set; withheld approvals delay but never remove devices; approvals never revive revoked bindings. An approval stays valid after its signer's revocation while its record remains; removing a revoked device's additions requires deleting their records. Every accepted, unrevoked device of a member account is eligible in every space the account belongs to; no per-space selection exists. Linking requires authenticated pairing plus confirmation of adding a device, with a warning that it can read all the account's spaces; a device-reported name is not treated as authenticated. |
| Repo observations | Verify the latest commit for current decisions against the current DID document across signing-key rotation and PDS migration; verify historical commits, including those embedded in grant evidence, against retained DID observations or a verifiable DID history such as the `did:plc` log, reporting them as incomplete audit evidence when no key can be established; cover a grant issued before rotation and read after it, which must still be accepted; retain the highest verified revision and commit CID per pinned account; reject lower revisions; alarm on a different commit at the retained revision. Presence only from inclusion proofs; absence only from a complete enumeration verified against a commit's MST root, or from verified commit events applied to one; record-level reads, errors, and unverifiable enumerations prove nothing. Ignore far-future revisions. Delete operations in authenticated commit events count as absence. |
| Revocation | Verified absence of a pinned binding's record, or a different binding at its device ID, revokes it permanently in every space; no device-signed revocation exists. Reappearance after observed deletion is ignored and alarms. Deletion followed by recreation between observations leaves the binding accepted on clients that missed it while others revoke it; a removed device whose session survives can recreate its own record. Standing application sessions are create-only for device and approval collections and never use `putRecord`; removal uses a separate short-lived delete authorization, after the user ends the device's session, followed by verified absence at a later commit and a second deletion with a warning if the record reappeared. On PDSes enforcing OAuth permissions, a create-only session cannot delete or overwrite other device records; app passwords, broad-scope applications, and the account password can, and recovery is through re-enrollment. UX never claims otherwise. A migration that drops device records revokes them. Preserve revocations across replay, restore, and future spaces. Revoked devices issue and receive no new grants; bindings they approved survive. Same-revision commit conflicts and present-absent-present sequences alarm; other divergent histories are not detected. |
| Re-enrollment | Only after every accepted binding of the account is verified revoked, and only for clients that knew the account. The candidate satisfies the single-root rule and waits `REENROLL_HOLD` on each client's local clock from first observation of that exact candidate; no grant or key acceptance in either direction before then. Replacing the candidate at hour 71 revokes its removed members and restarts the hold; imports merge start times only for identical candidates. Members see the pending device and their own client's earliest time; the recovering device shows only a minimum wait and per-space status. Own installations that verify their own record absent alarm. A malicious PDS hiding deletions from own installations is detected only by auditing grants. New contacts get plain first use. |
| Ending access | Space creation configures a read policy requiring delegation tokens; conforming applications never create one with a public read policy. Member removal ends credential issuance and access within one credential lifetime, sooner with `notifyCredentialRevoked`. Device revocation alone leaves Spaces access in place while the device holds a PDS session; removing its PDS access ends it within one credential lifetime. Every device-removal path, including own-account notices, tells the user to remove PDS access and never claims immediate cutoff. Shared application backends keep access through other members' sessions. |
| Space key | The creator generates a fresh random key and key ID, stores it durably before creation, and supplies `keyId`/`commitment` in the creating configuration. Grants and acceptance match the configuration's key ID and commitment; reject mismatches. The host rejects changes to `keyId`/`commitment`; clients reject a configuration whose values differ from those first observed as `INVALID`, keep the last valid configuration, and raise an integrity alarm, including after restart, migration, and restore. Removals, revocations, and suspected compromise block new grants but never change the key; removal and revocation notices never claim cryptographic exclusion, and removal flows neither default to nor prompt space replacement. A replacement space has a fresh key and reuses device trust without carrying content; republished content is the republisher's. Writers without the key retain drafts until a grant arrives. Loss of every key copy and backup makes the space unreadable and unwritable. |
| Distribution scheduling | Request-driven delivery: devices request keys for spaces they open; holders answer after randomized backoff; unrequested grants only to devices known to use the space, including the creator's prompt grants to its own same-application installations; no unrequested grants to other devices. Concurrent helpers, partial repo views, retries, and duplicates retain normal publication checks. Existing grants with unaccepted issuers, missing evidence, or bad ciphertext cannot permanently suppress alternatives. Requests usable without content keys remain non-authoritative, bounded hints; no exclusive issuer or complete-coverage claim. |
| Key requests | Publish unencrypted signed requests in the requester's space repo; discover through normal authenticated sync, notifications, offline catch-up, and periodic reconciliation without content keys. Reject bad schema/signature and account/space/location substitution; validate the configuration and the recipient binding's acceptance independently. A valid self-signed request cannot seed trust or bypass revocations, local trust checks, or grant publication/acceptance. Any/preferred issuers and requesting an alternative after an unusable grant; preferred issuer has no exclusive authority. Exact retries reuse bytes/identity; semantic deduplication, per-account bounds, randomized backoff, and reconsideration after authorization/key changes. Delete satisfied/abandoned/obsolete hints without audit gaps, evidence pruning, or a claim of receipt; exclude requests from evidence manifests. Suppression, denied access, and offline holders can prevent delivery; no delivery is promised. |
| Evidence and archives | Exact issuer/recipient bindings and approval paths, host decisions, actual retained bytes when source PDS withholds; no private trust history or cross-space provenance leakage, and no inherited trust. Historical reading after removals/revocations still checks signatures/bindings/evidence/commitment. Missing required evidence blocks; historical uncertainty alone need not block valid decryption but timestamps do not prove ordering. Archives never restore authority or access. |
| Publication retries | Durable bytes/identity before release, evidence-first upload, crashes before/after publication/ack, identical retries give one record. Changed bytes are new issuance. Recheck both parties/trust/revocations/evidence on retries/direct delivery, even after acknowledgment. Missing acknowledgment leaves exposure uncertain and forbids direct forwarding; stopped retries preserve published audit records. |
| Own-account device notices | Every own installation except the approver notifies the user of each new or removed own binding, including those approved by another own installation, learned from an approval, device record, revocation, or another issuer's grant. A grant in another issuer's repo triggers the notice when the account's own PDS hides the record. One notice per binding across all spaces. Removal from the notice takes the user to the PDS to delete the record and end the session, without rotating, and offers space replacement, since an unrecognized device suggests compromise. Notices are not integrity alarms and add no gate; existing alarms for bindings no own installation approved remain. Other members get no required notice for approved changes. |
| Auditing | First-contact substitution detected promptly through honest issuer repos and retained own history despite source withholding; alarms for grants to unapproved own bindings and for unaccepted approvals/device records in the local account's public repo, including when the account's PDS hides them from its own reads. Forged audit signatures, stale formerly authorized versus never-authorized keys, legitimate revisions, suppression/collusion, unknown history, observations versus grants. Signature attributes statement, not PDS misconduct or decryption. Review metadata and transferable-signature privacy. |
| Retention and sync | Indefinite grants, exact evidence, approvals, and revocations; preserve through migration/revocation/membership/restore. Host discovery plus retained participants, former repos while authorized, audit before key delivery, interrupted checkpoints/gaps, expiry/deletion/unavailable history. Offline catch-up, retained local auditing after removal without promised further access; no all-grants-seen claim. Background gaps neither bypass grant checks nor block unrelated work. |
| Recovery/transfer | Surviving approval of fresh keys, one eligible holder can restore spaces whose keys it holds without transferring trust to others. Without a surviving approver, the user removes every lost device at the PDS and re-enrolls after the hold. Reject revived revocations or re-invitation history reset. Authenticated/confidential keys plus pins/order/approvals/revocations, highest verified repo revisions, and first-observed configuration values; older imports preserve newer known state. Undetectable backup rollback retains its stated limits. Missing/incomparable history cannot invent prior acceptance; key-only restore cannot recreate trust; all copies lost means plaintext lost. |

### Procedure and transition coverage

| Procedure | Required mapping and additional cases |
| --- | --- |
| [G1–G5: exchange authorization](core.md#grant-authorization) | Trust establishment in G2 before G3 requires accepted bindings, so first contact can succeed. Host authority, trust on first use, approvals, revocations, re-enrollment holds, and locally current state. Both local roles; known denial versus missing evidence; valid readmission restores eligibility but never a revoked binding; no release before `OK`; authorization changes between validation and release. |
| [A1–A7: grant acceptance](core.md#grant-acceptance) | Encoding, trust, evidence/archives, and the space key. No decryption before required checks; compare the recipient's entire binding, including a substituted signing key with the same encryption key/ID. Both modes reject an ineligible recorded membership decision even after readmission. Missing mandatory evidence blocks; uncertainty about issuance timing or the issuer's then-known state alone need not block an archive. Later revocation alone does not invalidate history. A5 requires issuer acceptance in both modes; A7 rechecks newly learned state. No trust promotion. |
| [D1–D3: approvals](device-enrollment.md#approval-validation) | Approvals, repo observations, and recovery. Pending approvals apply atomically once their signer is accepted; unproven approval or target records return incomplete; accepted bindings survive their approver's later revocation; approvals of revoked targets have no effect; invalid input cannot erase state. |
| [P1–P8: publication](audit.md#publication) | Publication retries, evidence, and retention/sync. Every transition, partial uploads, acknowledgment loss, absent/different repo bytes, reauthorization before each release, and late acknowledgment after stopping. Stopping preserves prior exposure facts. |
